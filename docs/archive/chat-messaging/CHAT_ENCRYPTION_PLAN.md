# Chat Message Encryption — Architecture & Change Plan

## 1. Threat Model & Goals

| Goal | Detail |
|------|--------|
| **At-rest encryption** | Messages in the `chat_messages` DB table are never stored as plaintext |
| **In-transit encryption** | No plaintext travels between client and server (beyond TLS) |
| **Supabase cannot read** unless translation is ON and only during the ephemeral translate step |
| **Cross-device** | Any device with correct login credentials can read all messages |
| **Toggle-aware** | Switching translation ON/OFF adjusts encryption behavior seamlessly per message |
| **Backward compatible** | Existing plaintext messages remain readable alongside new encrypted ones |

## 2. Key Infrastructure

### Long-Term Keys

| Key | Type | Owner | Storage | Purpose |
|-----|------|-------|---------|---------|
| **User key pair** | X25519 | Each user | Device: `flutter_secure_storage` (hardware-backed); Server: public key in `user_keys` table | Encrypt/decrypt messages between users |
| **Supabase key pair** | X25519 | Supabase | Private key: Edge Function Secret; Public key: `app_config` table | One-time decryption for translation |
| **Password-derived key** | PBKDF2-SHA256 | Each user | Derived at login from password | Wraps the user's private key for cross-device sync |

### Per-Message Keys

| Key | Type | Generated By | Lifetime | Purpose |
|-----|------|-------------|----------|---------|
| **Message AES key** | AES-256-GCM (random) | Sender client | One message | Encrypts `content_original` (and later `content_translated`) |
| **Wrapped key (recipient)** | X25519 ECDH + HKDF wrapping | Sender client | Persistent in DB | Allows recipient to unwrap the AES key |
| **Wrapped key (Supabase)** | X25519 ECDH + HKDF wrapping | Sender client | Persistent in DB | Allows Supabase to unwrap the AES key for translation (only present when translation is ON) |

### user_keys Table (new)

```sql
CREATE TABLE user_keys (
  user_id       uuid PRIMARY KEY REFERENCES users(id),
  public_key    bytea NOT NULL,           -- X25519 public key (32 bytes)
  encrypted_private_key bytea NOT NULL,   -- Private key encrypted with password-derived key
  key_created_at timestamptz DEFAULT now(),
  key_rotation_count int DEFAULT 0
);
```

### chat_messages Table Changes (new columns)

```sql
ALTER TABLE chat_messages ADD COLUMN
  encryption_scheme              text DEFAULT 'plaintext',  -- 'plaintext' | 'v1'
  content_original_encrypted     bytea,                     -- AES-256-GCM ciphertext of original
  content_translated_encrypted   bytea,                     -- AES-256-GCM ciphertext of translation
  encryption_iv                  bytea,                     -- AES IV (12 bytes)
  encryption_iv_translated       bytea,                     -- AES IV for translated version
  wrapped_keys                   jsonb;                     -- { "recipient": "<base64>", "supabase": "<base64>" | null }
```

## 3. Per-Key Flows

### 3.1 User Registration / Key Generation

```
User signs up
  ├─ Generate X25519 key pair on device
  ├─ Store private key in flutter_secure_storage
  ├─ Derive PBKDF2 key from password (at time of entry)
  ├─ Encrypt private key with PBKDF2 key
  ├─ Upload public_key + encrypted_private_key to user_keys table
  └─ (Supabase public key is fetched from app_config and cached client-side)
```

### 3.2 Cross-Device Login

```
User signs in on new Device B
  ├─ Retrieve encrypted_private_key from user_keys table
  ├─ Derive same PBKDF2 key from password
  ├─ Decrypt private key
  ├─ Store private key in flutter_secure_storage on Device B
  └─ (All messages are decryptable via existing wrapped_keys in the DB)

Password change:
  ├─ Derive old key from old password, decrypt private key
  ├─ Derive new key from new password
  ├─ Re-encrypt private key
  └─ Update user_keys.encrypted_private_key
```

### 3.3 Sending a Message (Translation OFF)

```
Sender client:
  1. Generate random AES-256-GCM key K (32 bytes) and random IV (12 bytes)
  2. Encrypt plaintext: ciphertext = AES-256-GCM.encrypt(plaintext, K, IV, aad=matchId)
  3. Fetch recipient's public key from user_keys (or cached locally)
  4. ECDH: shared_secret = X25519(sender_private, recipient_public)
  5. HKDF-SHA256: wrapping_key = HKDF(shared_secret, salt: messageId, info: "matchme-msg-key")
  6. AES-KW: wrapped_key_recipient = AESKeyWrap(wrapping_key, K)
  7. Send to Supabase:
     {
       match_id,
       sender_id,
       content_original_encrypted: ciphertext,
       encryption_iv: IV,
       wrapped_keys: { "recipient": wrapped_key_recipient },
       encryption_scheme: "v1"
     }

Supabase:
  1. INSERT into chat_messages -- stores opaque blob, cannot read
  2. Realtime broadcasts the new row (still opaque)
  3. Push notification triggered (contains no message content)
```

### 3.4 Sending a Message (Translation ON)

```
Sender client:
  1. Same as 3.3 steps 1-6
  2. Additionally:
     a. ECDH: supabase_shared = X25519(sender_private, supabase_public)
     b. HKDF: supabase_wrapping = HKDF(supabase_shared, salt: messageId, info: "matchme-supabase-key")
     c. AES-KW: wrapped_key_supabase = AESKeyWrap(supabase_wrapping, K)
  3. Send:
     {
       match_id,
       sender_id,
       content_original_encrypted: ciphertext,
       encryption_iv: IV,
       wrapped_keys: {
         "recipient": wrapped_key_recipient,
         "supabase": wrapped_key_supabase
       },
       encryption_scheme: "v1"
     }
```

### 3.5 Receiving a Message

```
Recipient client:
  1. Realtime subscription receives new row (encrypted blob)
  2. Check encryption_scheme:
     - "plaintext" → read existing content_original, content_translated (backward compat)
     - "v1" → proceed below
  3. Fetch sender's public key from user_keys (or cached)
  4. ECDH: shared_secret = X25519(recipient_private, sender_public)
  5. HKDF: wrapping_key = HKDF(shared_secret, salt: messageId, info: "matchme-msg-key")
  6. AES-KW unwrap: K = AESKeyUnwrap(wrapping_key, wrapped_keys.recipient)
  7. AES-256-GCM decrypt: plaintext = AES-256-GCM.decrypt(content_original_encrypted, K, IV, aad=matchId)
  8. If content_translated_encrypted exists:
     a. Use same K (or separate K' if re-encrypted) → decrypt translated version
  9. Cache decrypted result in Hive for offline/performance
  10. Display in UI
```

### 3.6 Translation via Supabase Edge Function

```
Trigger: INSERT on chat_messages WHERE wrapped_keys->>'supabase' IS NOT NULL

translate-proxy Edge Function:
  1. Receive new row via webhook
  2. Check wrapped_keys.supabase exists → translation is ON for this message
  3. ECDH: shared = X25519(supabase_private, sender_public)
     (pre-computed and cached per sender for performance)
  4. HKDF: wrapping = HKDF(shared, salt: messageId, info: "matchme-supabase-key")
  5. AES-KW unwrap: K = AESKeyUnwrap(wrapping, wrapped_keys.supabase)
  6. AES-256-GCM decrypt: plaintext = decrypt(content_original_encrypted, K, IV)
  7. [IN MEMORY ONLY — never written to DB]:
     a. Send plaintext to DeepL API → get translated_text
     b. Detect source_language, target_language
  8. Encrypt translated result:
     a. Either use same K (simpler, recommended):
        translated_ciphertext = AES-256-GCM.encrypt(translated_text, K, NEW_IV_translated)
     b. Or generate new K_translated and wrap it (if key separation is desired)
  9. UPDATE chat_messages SET
       content_translated_encrypted = translated_ciphertext,
       encryption_iv_translated = new_iv,
       detected_source_language = src_lang,
       translated_target_language = tgt_lang
     WHERE id = messageId
  10. Zeroize K, plaintext, translated_text from memory
  11. Return success
```

### 3.7 On-the-Fly Translation of Old Messages (Toggle Turned ON)

```
User enables translation for a chat:

Client:
  1. Gather all visible message IDs that lack content_translated_encrypted
  2. Generate temporary AES key K_batch
  3. ECDH with Supabase public key → wrap K_batch
  4. Send batch request to translate-proxy:
     {
       message_ids: [...],
       wrapped_key_supabase: <wrapped K_batch>,
       encryption_iv_pairs: { msgId: iv, ... },
       content_encrypted_pairs: { msgId: ciphertext, ... },
       target_language: "es"
     }
  5. Protect: re-encrypt each message's original from Hive with K_batch
     (since they're already decrypted in local cache)

Edge Function:
  1. Unwrap K_batch using Supabase private key
  2. For each message:
     a. Decrypt the re-encrypted original
     b. Send to DeepL
     c. Encrypt result with K_batch (or generate per-message sub-keys)
  3. Batch UPDATE: store encrypted translations + proper wrapped_keys for recipient
  4. Return results

Client:
  1. Decrypt results using K_batch
  2. Update Hive cache
  3. Display translated content
  4. Future views: content_translated_encrypted is in DB → use standard receive flow (3.5)
```

### 3.8 Toggle OFF → ON Transition

```
Toggle ON:
  ├─ All NEW messages include wrapped_keys.supabase (only Supabase can decrypt for translation)
  ├─ OLD messages remain as-is (already encrypted without supabase wrapping)
  └─ On-the-fly flow (3.7) handles translating old messages when viewed

Toggle OFF:
  ├─ All NEW messages omit wrapped_keys.supabase (Supabase cannot decrypt)
  ├─ OLD messages still have wrapped_keys.supabase in their stored row
  ├─ Client detects: if wrapped_keys has "supabase" → translation was ON at send time
  └─ Nothing to do — old messages already have their encrypted translations stored
```

## 5. Message Flow Summary (All States)

### State A: Translation OFF → E2E Only

```
Sender ───(encrypted)──→ Supabase ──(encrypted)──→ Recipient
         can't read             can't read
```

### State B: Translation ON (new message from sender)

```
Sender ──(encrypted + Supabase-wrapped key)──→ Supabase
                                                  │
                                          decrypt in memory
                                                  │
                                          ┌──────┴──────┐
                                          │    DeepL     │
                                          └──────┬──────┘
                                                  │
                                          encrypt results
                                                  │
                    ┌─────────────────────────────┤
                    │                             │
          store encrypted                  realtime push
          original + translated            (encrypted)
                    │                             │
                    ▼                             ▼
                  DB ─────────────────→ Recipient decrypts both
```

### State C: Viewing Old Messages After Toggle OFF→ON

```
Recipient local cache (already decrypted)
                    │
          re-encrypt with Supabase public key
                    │
          ┌────────┴────────┐
          │ translate-proxy  │
          │ (decrypt→DeepL   │
          │  →encrypt→store) │
          └────────┬────────┘
                    │
          content_translated_encrypted now in DB
                    │
          Future views: standard receive flow (decrypt locally)
```

### State D: Cross-Device Login

```
Device B login
  ├─ Fetch encrypted_private_key from user_keys
  ├─ Derive PBKDF2 key from entered password
  ├─ Decrypt private key → store in flutter_secure_storage
  ├─ Fetch all chat_messages (encrypted blobs)
  ├─ For each: fetch sender public_key, ECDH unwrap, AES decrypt
  ├─ Cache decrypted in Hive
  └─ UI displays as normal
```

## 6. Security Properties

| Property | Achieved? | How |
|----------|-----------|-----|
| **At-rest confidentiality** | ✅ | AES-256-GCM ciphertext in DB; no plaintext columns |
| **Server cannot read (translation OFF)** | ✅ | No `wrapped_keys.supabase` → Supabase cannot unwrap the AES key |
| **One-time server read (translation ON)** | ✅ | Only during Edge Function invocation; plaintext never persisted |
| **Forward secrecy** | ❌ (not required) | Long-term X25519 keys mean past messages can be decrypted if a private key is compromised. Could add X3DH/Double Ratchet for forward secrecy — major complexity increase |
| **Cross-device recovery** | ✅ | Password-derived PBKDF2 key unlocks the encrypted private key |
| **No plaintext in transit** | ✅ | Client-to-server sends ciphertext; server-to-client sends ciphertext |
| **Integrity / authentication** | ✅ | AES-GCM provides authenticated encryption (detects tampering) |
| **Backward compatibility** | ✅ | `encryption_scheme: 'plaintext'` → read old columns; `'v1'` → decrypt path |
| **Replay resistance** | ✅ | Each message has unique IV; AAD includes `match_id` |
